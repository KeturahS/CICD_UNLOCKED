למד את המושגים והכלים המרכזיים בעולם של Jenkins

מבוא ל-Jenkins

J
מהו Jenkins?

Jenkins הוא שרת אוטומציה בקוד פתוח (Open Source) שמאפשר למפתחים לאוטומט את תהליכי הפיתוח, הבדיקות והפריסה של תוכנה. הוא מהווה כלי מרכזי בעולם ה-CI/CD (אינטגרציה מתמשכת / פריסה מתמשכת).

Jenkins נוצר במקור ב-2004 תחת השם "Hudson" על ידי קוהסוקה קאוואגוצ'י בחברת Sun Microsystems. לאחר שאורקל רכשה את Sun, הפרויקט פוצל ושונה שמו ל-Jenkins ב-2011.

למה משתמשים ב-Jenkins?

  • אוטומציה: מאפשר להפוך תהליכים ידניים לאוטומטיים
  • אינטגרציה מתמשכת (CI): בדיקה אוטומטית של שינויים בקוד
  • פריסה מתמשכת (CD): העברה אוטומטית של קוד לסביבות שונות
  • גמישות: תומך במגוון רחב של כלים ושפות תכנות
  • הרחבה: אלפי תוספים (plugins) זמינים להרחבת הפונקציונליות
  • קהילה גדולה: תמיכה נרחבת וידע רב זמין ברשת

איך Jenkins עובד?

Jenkins פועל כשרת שמריץ תהליכים מוגדרים (ג'ובים) על פי טריגרים שונים. הוא יכול לפעול כך:

  1. מפתח דוחף שינויים למאגר קוד (כמו Git)
  2. Jenkins מזהה את השינוי (באמצעות webhook או סריקה תקופתית)
  3. Jenkins מריץ ג'וב שמוגדר מראש (למשל: בניית הקוד, הרצת בדיקות)
  4. Jenkins מדווח על תוצאות התהליך (הצלחה/כישלון)
  5. במקרה של הצלחה, Jenkins יכול להמשיך לשלבים הבאים (למשל: פריסה לסביבת בדיקות)

הדגמה: תהליך בסיסי ב-Jenkins

לחצו על השלבים השונים כדי לראות מה קורה בכל שלב:

דחיפת קוד
בנייה
בדיקות

דחיפת קוד

מפתח מסיים לכתוב קוד ודוחף אותו למאגר הקוד (Git, SVN וכו'). פעולה זו מפעילה טריגר ב-Jenkins.

דוגמה לפקודה:

git push origin main

בנייה (Build)

Jenkins מושך את הקוד העדכני ומבצע תהליך בנייה. זה יכול לכלול קומפילציה, יצירת חבילות וכו'.

דוגמה לפקודות בשלב זה:

npm install npm run build

בדיקות (Test)

Jenkins מריץ בדיקות אוטומטיות על הקוד כדי לוודא שהוא עובד כמצופה ושלא נוצרו באגים חדשים.

דוגמה לפקודות בשלב זה:

npm test npm run lint

פריסה (Deploy)

אם כל הבדיקות עברו בהצלחה, Jenkins מפרס את הקוד לסביבה הרלוונטית (פיתוח, בדיקות, ייצור).

דוגמה לפקודות בשלב זה:

ssh user@server 'cd /app && git pull' docker-compose up -d

מושגים מרכזיים ב-Jenkins

J
Job (ג'וב)

ג'וב הוא תהליך מוגדר שמריצים ב-Jenkins. זהו הבסיס לכל פעולה אוטומטית במערכת.

סוגי ג'ובים:

  • Freestyle: ג'וב פשוט שמוגדר דרך ממשק המשתמש
  • Pipeline: ג'וב מורכב שמוגדר באמצעות קוד
  • Multi-configuration: ג'וב שרץ במספר קונפיגורציות שונות
  • Folder: מאפשר ארגון של ג'ובים בתיקיות
  • Multi-branch Pipeline: פייפליין שרץ על מספר ענפים (branches) במאגר הקוד

P
Pipeline

פייפליין הוא סדרה של שלבים (Stages) שמגדירים תהליך CI/CD שלם. הוא מאפשר להגדיר את כל התהליך כקוד (Pipeline as Code) בקובץ Jenkinsfile.

יתרונות:

  • הגדרת התהליך כקוד שניתן לשמור במאגר
  • חלוקה לוגית לשלבים (Stages)
  • תמיכה בתהליכים מקבילים
  • ויזואליזציה טובה של התהליך

F
Jenkinsfile

קובץ טקסט (בדרך כלל בשפת Groovy) שמכיל את הגדרת הפייפליין. הקובץ נשמר במאגר הקוד ומגדיר את כל השלבים והפעולות שיש לבצע.

דוגמה בסיסית:

pipeline { agent any stages { stage('Build') { steps { sh 'npm install' sh 'npm run build' } } stage('Test') { steps { sh 'npm test' } } stage('Deploy') { steps { sh 'npm run deploy' } } } }

S
Stage / Step

Stage (שלב): חלק לוגי בפייפליין שמכיל צעדים קשורים (למשל: בנייה, בדיקות, פריסה).

Step (צעד): פעולה בודדת בתוך שלב (למשל: הרצת פקודה, הורדת קוד ממאגר).

הפרדה זו מאפשרת ארגון ברור של התהליך וויזואליזציה טובה יותר.

A
Agent

Agent הוא מחשב (שרת או מכונה וירטואלית) ש-Jenkins משתמש בו כדי להריץ ג'ובים. ניתן להגדיר סוגים שונים של agents:

  • any: כל agent זמין
  • none: לא משתמש ב-agent (למשל בפייפליין שמגדיר רק את המבנה)
  • label: agent עם תווית מסוימת
  • docker: מיכל דוקר
  • kubernetes: פוד ב-Kubernetes

N
Node

Node הוא מחשב שמחובר לשרת Jenkins ויכול להריץ ג'ובים. יכול להיות ה-master (כיום נקרא controller) או slave (כיום נקרא agent).

סוגי Nodes:

  • Controller (Master): השרת המרכזי שמנהל את התהליכים
  • Agent (Slave): שרת משני שמריץ ג'ובים

שימוש במספר nodes מאפשר הרצת ג'ובים במקביל ושיפור הביצועים.

P
Plugin (תוסף)

Jenkins תומך באלפי תוספים שמרחיבים את הפונקציונליות שלו. תוספים מאפשרים אינטגרציה עם כלים וטכנולוגיות שונות.

תוספים נפוצים:

  • Git: אינטגרציה עם מאגרי Git
  • Docker: תמיכה בבניית ופריסת מיכלי Docker
  • Pipeline: תמיכה בפייפליינים
  • Blue Ocean: ממשק משתמש מודרני
  • JUnit: תמיכה בדוחות בדיקות
  • Slack: שליחת התראות ל-Slack

B
Build

Build הוא הרצה בודדת של ג'וב או פייפליין. לכל build יש מספר ייחודי והוא שומר את התוצאות, הלוגים והארטיפקטים שנוצרו במהלך ההרצה.

ניתן לראות את היסטוריית ה-builds של כל ג'וב ולנתח את התוצאות והמגמות לאורך זמן.

W
Workspace

Workspace הוא תיקייה זמנית על ה-agent שבה נשמרים הקבצים במהלך ההרצה של ג'וב. זהו המקום שבו Jenkins מוריד את הקוד ממאגר הקוד ומבצע את הפעולות השונות.

כל ג'וב מקבל workspace משלו, וניתן לנקות אותו בין הרצות כדי לחסוך מקום.

S
SCM (Source Control Management)

Jenkins משתלב עם מערכות ניהול קוד כמו Git, SVN ואחרות. אינטגרציה זו מאפשרת ל-Jenkins למשוך את הקוד העדכני ולהגיב לשינויים במאגר.

ניתן להגדיר טריגרים שיפעילו ג'ובים כאשר יש שינויים במאגר הקוד.

T
Trigger

Trigger הוא אירוע שגורם להרצה אוטומטית של ג'וב. קיימים מספר סוגי טריגרים:

  • Poll SCM: בדיקה תקופתית של שינויים במאגר הקוד
  • Webhook: הפעלה על ידי שירות חיצוני (למשל GitHub)
  • Cron: הפעלה על פי לוח זמנים מוגדר
  • Upstream/Downstream: הפעלה לאחר סיום של ג'וב אחר
  • Manual: הפעלה ידנית על ידי משתמש

B
Blue Ocean

Blue Ocean הוא ממשק משתמש מודרני ל-Jenkins שמציג את הפייפליינים בצורה גרפית ברורה. הוא מאפשר ניווט קל יותר ומספק חוויית משתמש משופרת.

Blue Ocean מתמקד בפייפליינים ומציג את השלבים השונים, הזמנים והתוצאות בצורה ויזואלית.

A
Artifact

Artifact הוא תוצר של הרצת ג'וב (למשל: קובץ JAR, חבילת NPM, דוח בדיקות) שנשמר להורדה או הפצה. Jenkins מאפשר לשמור ארטיפקטים ולהשתמש בהם בג'ובים אחרים.

ארטיפקטים מאפשרים העברת תוצרים בין שלבים שונים בתהליך ושמירה על היסטוריה של הבניות.

פייפליינים ב-Jenkins

מהם פייפליינים?

פייפליינים (Pipelines) הם למעשה "צינורות" או "קווי ייצור" דיגיטליים שמגדירים סדרה של שלבים אוטומטיים בתהליך פיתוח התוכנה.

דמיינו מפעל שבו המוצר עובר בין תחנות שונות בפס הייצור - כל תחנה מבצעת פעולה מסוימת על המוצר עד שהוא מוכן. באופן דומה, פייפליין בג'נקינס מעביר את קוד התוכנה דרך שלבים שונים.

סוגי פייפליינים

ב-Jenkins קיימים שני סוגים עיקריים של פייפליינים:

  • Declarative Pipeline: תחביר פשוט יותר שמבוסס על מבנה מוגדר מראש
  • Scripted Pipeline: תחביר גמיש יותר שמבוסס על שפת Groovy

מבנה בסיסי של פייפליין

pipeline { agent any // איפה להריץ את הפייפליין stages { // הגדרת השלבים stage('Build') { // שלב הבנייה steps { // הצעדים בשלב echo 'בונה את הפרויקט...' sh 'npm install' sh 'npm run build' } } stage('Test') { // שלב הבדיקות steps { echo 'בודק את הפרויקט...' sh 'npm test' } } stage('Deploy') { // שלב הפריסה steps { echo 'מפרס את הפרויקט...' sh 'npm run deploy' } } } post { // פעולות לאחר סיום הפייפליין success { echo 'הפייפליין הושלם בהצלחה!' } failure { echo 'הפייפליין נכשל!' } } }

רכיבים מרכזיים בפייפליין

  • pipeline: הבלוק העליון שמכיל את כל הגדרות הפייפליין
  • agent: מגדיר איפה הפייפליין ירוץ
  • stages: מכיל את כל השלבים של הפייפליין
  • stage: מגדיר שלב בודד בפייפליין
  • steps: מגדיר את הפעולות שיש לבצע בשלב
  • post: מגדיר פעולות שיש לבצע לאחר סיום הפייפליין

פייפליין מתקדם יותר

pipeline { agent { docker { image 'node:14' } } environment { HOME = '.' NPM_CONFIG_CACHE = "${env.WORKSPACE}/.npm" } stages { stage('Checkout') { steps { checkout scm } } stage('Install') { steps { sh 'npm ci' } } stage('Lint') { steps { sh 'npm run lint' } } stage('Test') { steps { sh 'npm test' } post { always { junit 'test-results/*.xml' } } } stage('Build') { steps { sh 'npm run build' } } stage('Deploy') { when { branch 'main' } steps { sh 'npm run deploy' } } } post { success { slackSend channel: '#builds', color: 'good', message: "הבנייה הצליחה: ${env.JOB_NAME} #${env.BUILD_NUMBER}" } failure { slackSend channel: '#builds', color: 'danger', message: "הבנייה נכשלה: ${env.JOB_NAME} #${env.BUILD_NUMBER}" } always { archiveArtifacts artifacts: 'dist/**/*', fingerprint: true cleanWs() } } }

תכונות מתקדמות בפייפליינים

  • Parallel: הרצת שלבים במקביל
  • When: הרצת שלב רק בתנאים מסוימים
  • Parameters: הגדרת פרמטרים לפייפליין
  • Input: בקשת קלט מהמשתמש במהלך הפייפליין
  • Shared Libraries: שימוש בספריות משותפות

דוגמה לפייפליין עם הרצה במקביל

pipeline { agent any stages { stage('Build') { steps { echo 'בונה את הפרויקט...' } } stage('Test') { parallel { stage('Unit Tests') { steps { echo 'מריץ בדיקות יחידה...' } } stage('Integration Tests') { steps { echo 'מריץ בדיקות אינטגרציה...' } } stage('Performance Tests') { steps { echo 'מריץ בדיקות ביצועים...' } } } } stage('Deploy') { steps { echo 'מפרס את הפרויקט...' } } } }

שימוש ב-Jenkinsfile

הדרך המומלצת לעבוד עם פייפליינים היא באמצעות קובץ Jenkinsfile שנשמר במאגר הקוד. יתרונות הגישה:

  • הגדרת הפייפליין כקוד (Pipeline as Code)
  • גרסאות ומעקב אחר שינויים
  • סקירת קוד (Code Review) על הפייפליין
  • שימוש חוזר ושיתוף של פייפליינים

תוספים (Plugins) ב-Jenkins

מהם תוספים?

תוספים (Plugins) הם הרחבות ל-Jenkins שמוסיפות פונקציונליות חדשה או משפרות את הפונקציונליות הקיימת. Jenkins מגיע עם מספר תוספים בסיסיים, אך ניתן להתקין אלפי תוספים נוספים.

תוספים נפוצים

G
Git Plugin

מאפשר אינטגרציה עם מאגרי Git. זהו אחד התוספים הנפוצים ביותר והוא מאפשר ל-Jenkins למשוך קוד ממאגרי Git ולהגיב לשינויים בהם.

P
Pipeline Plugin

מאפשר שימוש בפייפליינים ב-Jenkins. זהו תוסף מרכזי שמספק את התשתית לפייפליינים ואת התמיכה בקובצי Jenkinsfile.

D
Docker Plugin

מאפשר שימוש במיכלי Docker כ-agents וכן בניית ופריסת מיכלי Docker. תוסף זה שימושי מאוד בסביבות מודרניות שמשתמשות ב-Docker.

B
Blue Ocean Plugin

מספק ממשק משתמש מודרני וויזואלי ל-Jenkins, עם דגש על פייפליינים. הממשק מאפשר ניווט קל יותר וחוויית משתמש משופרת.

J
JUnit Plugin

מאפשר הצגה וניתוח של תוצאות בדיקות JUnit. תוסף זה שימושי מאוד לפרויקטים שמשתמשים בבדיקות אוטומטיות.

S
Slack Notification Plugin

מאפשר שליחת התראות ל-Slack על אירועים ב-Jenkins (למשל: בנייה הצליחה/נכשלה). תוסף זה מאפשר אינטגרציה טובה יותר עם צוותי פיתוח.

התקנת תוספים

ניתן להתקין תוספים ב-Jenkins בשתי דרכים עיקריות:

  1. דרך ממשק המשתמש: Manage Jenkins > Manage Plugins > Available
  2. באמצעות Jenkins CLI: שימוש בפקודה jenkins-cli.jar install-plugin

ניהול תוספים

ניהול נכון של תוספים חשוב לשמירה על יציבות ואבטחה של שרת Jenkins:

  • עדכון תוספים באופן קבוע
  • הסרת תוספים שאינם בשימוש
  • בדיקת תאימות בין תוספים
  • גיבוי הגדרות לפני התקנת תוספים חדשים

השלמת פייפליין

גרור את חלקי הקוד למקומות המתאימים בפייפליין:

משימה: השלם את הפייפליין על ידי גרירת החלקים הנכונים למקומות המסומנים.

חלקי קוד זמינים:

הפייפליין שלך:

pipeline {
    agent any
    
    stages {
גרור לכאן את שלב ה-Checkout
גרור לכאן את שלב ה-Build
גרור לכאן את שלב ה-Test
גרור לכאן את שלב ה-Deploy
    }
}

רמז:

  • שלב ה-Checkout צריך למשוך את הקוד ממאגר Git
  • שלב ה-Build צריך להתקין חבילות ולבנות את הפרויקט
  • שלב ה-Test צריך להריץ בדיקות
  • שלב ה-Deploy צריך לרוץ רק אם הענף הוא main
